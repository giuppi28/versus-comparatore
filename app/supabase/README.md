## Access model

- **anon** (publishable key): `select` on active `suppliers`, active `offers` whose supplier is
  active, all `comuni`. No privilege at all on `leads`, `settings`, `admins`.
- **Leads** only through `SECURITY DEFINER` functions (`search_path = ''`), executable by
  `anon`/`authenticated` only:
  - `create_lead(p_data jsonb) -> {"id","token"}`: requires `privacy_consent: true` (JSON boolean),
    else `privacy_consent_required`. Token = 32 random bytes, hex (256 bit).
  - `update_lead(p_token text, p_patch jsonb) -> void`: only the **in-progress** lead owning the
    token; otherwise `lead_not_found` (also for completed leads).
  - `complete_lead(p_token text, p_data jsonb) -> {"id","token"}`: writes data, checks required
    fields (`missing_field: <name>`), sets `step_reached = 'completed'`, `status = 'new'`.
    Afterwards the lead is read-only for anon.
  - Writable keys: every `LeadData` column (see `private.lead_writable_fields()`). Any other key
    (`status`, `notes`, `token`, `id`, timestamps…) → `invalid_field: <key>`.
    `step_reached` only moves forward (a backward value is ignored); `completed` is rejected
    (`invalid_step_reached`). `privacy_consent: false` → `privacy_consent_required`.
    Chosen offers must exist with the right commodity (`invalid_offer`). Patch > 20 kB →
    `payload_too_large`. Empty strings become NULL; `tax_code` and `pod` are upper-cased.
  - Column checks mirror `app/src/lib/lead/schemas.ts`: `people` 1–5, `appliances` / `gas_uses`
    only ids from `config/consumption.ts`, `power_kw` ∈ {1.5, 3, 3.5, 4, 4.5, 5, 6, 10, 15} or
    NULL ("Altro"), `voltage` 220/380. `estimated_kwh_year` / `estimated_smc_year` store the
    annual figure actually used (estimated or manual, flag `manual_consumption`).
- **Admin** = Supabase Auth user with a row in `public.admins` (create it manually:
  `insert into public.admins (user_id) values ('<auth.users.id>');`). `public.is_admin()`
  (SECURITY DEFINER, STABLE, executable by `authenticated`) backs all admin policies:
  full access to every table except `admins` (read own row only; no API writes).
- **MFA**: restrictive policies on every table for `authenticated`: if the user has a
  **verified** factor in `auth.mfa_factors`, the session must be `aal2`
  (`private.mfa_satisfied()`); users without a verified factor are unaffected.
  `is_admin()` itself does not depend on `aal`.
- **Public sign-up must be disabled** in Supabase Auth settings (dashboard).

## Comuni dataset (T1.3)

Generated by `python3 -I app/supabase/scripts/build_comuni.py` (stdlib only).

| Source | Used for | License |
|---|---|---|
| ISTAT, *Elenco comuni italiani* (`Elenco-comuni-italiani.xlsx`, sheet "CODICI al 21_02_2026") — https://www.istat.it/classificazione/codici-dei-comuni-delle-province-e-delle-regioni/ | list of comuni, ISTAT code, Italian name, province (sigla + name), region | CC BY 4.0 (Istat) |
| ISTAT, *Variazioni amministrative e territoriali dal 1991* (zip/csv) | predecessors of comuni renamed / merged / moved after Tabella A | CC BY 4.0 (Istat) |
| Samurai016/Comuni-ITA `data/comuni.json`, commit `433eb7e707ea9e04bf3859610a40e098f4f82ba5` — https://github.com/Samurai016/Comuni-ITA | CAP list (`cap` ∪ `capAlternativi`) | MIT |
| DPR 412/93 *Tabella A* (as updated, last change DM 27/06/2016), via Openpolis "Le zone climatiche dei comuni italiani" (Flourish table 11460270, "elaborazione openpolis su dati Mite") — https://www.openpolis.it/numeri/le-zone-climatiche-dei-comuni-italiani/ | climate zone A–F | The zones are content of an official act (not copyrightable, art. 5 L. 633/1941); Openpolis publishes its pages under CC BY-NC 4.0 — see open issue below |

Field mapping: `name` = "Denominazione in italiano" (e.g. "Bolzano"), `province_code` = sigla
automobilistica, `province_name` / `region` = Italian part of bilingual names
("Trentino-Alto Adige", "Valle d'Aosta"). `name_search` is a generated column
(`normalize_search(name)`), indexed with pg_trgm (GIN) and `text_pattern_ops`.

matches only (then 151 comuni have no zone).

## Local validation

No Docker / Supabase CLI / psql on the dev machine, so the SQL is validated with PGlite
(Postgres 18 compiled to WASM, with pgcrypto/pg_trgm/unaccent) on top of a stub that
emulates Supabase roles, `auth.uid()`, `auth.jwt()`, `auth.users`, `auth.mfa_factors` and the
default privileges:

```
mkdir -p /tmp/pgl && (cd /tmp/pgl && npm i @electric-sql/pglite@0.5)
PGLITE_DIR=/tmp/pgl node app/supabase/tests/run_local.mjs
```

It applies all migrations, runs `seed.sql` twice (idempotency), `tests/data_checks.sql`
and `tests/rls_test.sql`. Features used are available on Postgres 15 (Supabase).
